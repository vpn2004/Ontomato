## 交付内容与复杂问题保护

1. 新增 `getQueryContext(classes)`，一次取得指定对象的字段、直接关系、DSL 规则、适配器示例和约束。同一调用读取同一个领域本体快照；保留原有探索工具，模型可继续查找其他对象、关系和取值。正式复杂题实际使用了合并工具及补充探索。
2. 提示词明确谓词对象格式、存储关系方向、已完成关系查询的复用及 `writeFile` 的 `runAfter` 用法，减少重新构造原始外键、单独执行文件等重复调用。结果为空、含糊、冲突或不完整时仍要求继续验证。
3. DSL 防空转从“整个任务累计失败”改为“同一个规范化计划反复失败”。修改后的计划可以继续执行，成功清除失败记录。规范化忽略问题措辞、稳定排序 JSON 对象键；并发预留与会话隔离保留。没有新增总轮次上限，没有缩短任务执行时限。
4. 增加可选 `qualityCheck` 模型绑定，页面显示“问数质检”。空值沿用 `query`，独立模型保留自己的参数，不影响查询或编程模型；旧客户端只保存原有角色时不会清除新增绑定。正式环境均保持继承配置。
5. 程序解释完成一份就持久化并通过 SSE 发送一份，保留原程序索引。Node 和 Java 等待质检改为“连续 60 秒没有新解释才超时”；新解释续期，心跳和相同解释不续期。最终结论必须等综合质检真正完成，不能用部分证据冒充通过。

这里没有承诺无限执行：既有单次 DSL 能力、行数、任务及模型调用边界仍在。多次查询和经过测试的 Python 计算仍可组合使用；单个解释或最终评分模型若长时间没有新证据，仍可能触发空闲超时。这是后续需要通过持久任务恢复机制完善的边界，不能把本次验收说成今后绝不会超时。

## 快速质检未启用及下一轮安排

完成 18 次真实模型探针：两份完整程序解释、一次完整正例综合评分，以及漏过滤、错误去重、反向关系、日期边界、空值计数和单位换算六类反例，各对照当前模式与候选快速模式。

完整解释的输入约 1.36～1.37 万 token；快速模式约 5.06/5.66 秒，当前模式约 16.69/19.25 秒。正例评分约 3.75 对 27.47 秒，但速度收益不足以通过正确性门槛：把 17 个去重产品错误报为 34 行的反例，快速/当前模式分别给 62/65 分；日期边界错误的当前模式也给了 65 分。

现有提示词明确将“影响结果的重要偏差”放入 60～74 分，应用又以 60 分及格，并可能生成 MetricView。**这是已有的 Ontomato 判定规则问题，不能只归咎于快速模型，也不是 ONN 缺陷。** 本轮保留评分语义，没有启用快速模式；本次正确性以独立数据真值验收，不仅依赖模型分数。

下一轮按以下顺序继续，仍采用 TDD 和隔离 E2E：

1. 明确质检状态语义：正确、部分回答、明确错误应分开；明确错误不能因分数达到 60 而进入可信复用。先确认这一业务规则，再补反例回归、修改判定和 MetricView 入口。
2. 缩减解释模型的重复输入：仅提供本次程序实际使用的语法、关系与执行证据，保留必要上下文并允许补取。候选小模型/非思考模式继续通过完整程序和语义反例后再启用，不能只测短提示词。
3. 完善长任务恢复：将前台等待与后台质检完成分离，支持持久化进度、断线重连与晚到结论恢复。覆盖单个模型超过 60 秒、多程序排队、取消与进程重启，避免把长时间正确工作当作失败。
4. 有边界地复用已验证计划：按本体、权限和适配能力版本失效，每次重读实时数据；未知复杂题回退完整规划，不以固定轮数强行结束。

本轮没有新增 ONN Core 阻塞需求。若进一步拆分数据库耗时，需要独立提出 queryId 与服务端耗时字段等可观测性需求，不要求 ONN 团队改动模型规划或质检逻辑。
