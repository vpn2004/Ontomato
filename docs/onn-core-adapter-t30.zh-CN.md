# ONN adapter T30 接入与验收

日期：2026-11-06。基于 v4.1.1 的 `feature/onn-core-native-query`；仅改 adapter 及其测试、文档。

## 交付与部署边界

T30 Linux 固定包已通过 108 隔离验收，并不代表原有 ONN 服务已经切换。本轮使用同一个固定包另建临时实例及独立 Workbench/Data Engine 联调，未替换物流、质量生产服务。未修改 onn-core 目录，也没有部署本地未提交的 `LiveInstanceGraph.java`。

固定 Linux OMS SHA256：`0f0f5173bdbd06a9ef74655a3a3d667d0ad9faf5cb571b27bad445b5bceb1b8c`。
不单凭 `v13.0.0` 版本号启用功能；必须协商已启用的 `query_pushdown/v1`、日期/空值语义、快照及 pipeline 契约。未知或关闭的新契约沿用旧读取路径，授权和查询错误不触发成功空集降级。

## 已实现

| 能力 | 行为 |
|---|---|
| 响应兼容 | 支持 data、bindings、metrics、return；显式开启单页免会话；超页保持原 cursor、预算、完整消费和 close 行为 |
| schema 缓存 | 保留完整强 ETag，支持 304 空响应；热查询只在返回答案前重新验证一次，冷查询仍需要首次读取及终检 |
| capabilities 缓存 | 最多缓存 5 秒，构建/契约身份变化使缓存失效并拒绝当前查询；按 endpoint、凭证摘要、完整调用身份头隔离，最多 64 个身份范围 |
| 缓存安全 | 不缓存业务结果或授权决定；每次查询由 Core 重新授权；schema 改变或查询异常使元数据失效。无 ETag 的旧后端仍使用完整 schema 读取 |
| 明确计数 | 等价的 `COUNT(id)` 和 `COUNT(DISTINCT id)` 使用 metrics-only，下载 0 个对象；支持完整下推的筛选，保留输出窗口语义 |
| 过滤 | 支持已核对的布尔/字符串等值及 IN、日期绝对时刻比较、BETWEEN、IS NULL/IS NOT NULL；否定条件增加非空约束 |
| 数值范围 | Core 目前采用 double 范围比较，先向外扩展一个 ULP 选候选，再保留精确本地判断；不把该条件用于精确计数或聚合下推 |
| 字段投影 | 单类保留所有本地计算依赖；图查询通过 binding_output 仅返回输出、条件、排序、分组和 HAVING 所需属性，身份仍保留 |
| 聚合 | pipeline return 支持全局对象/路径计数、非空属性计数；身份 DISTINCT 用 objects，普通计数用 paths；支持具有完整分组键排序的布尔/整型分组计数 |
| 证据 | 输出 resultKind、实际 filter/projection/aggregatePushdown、本地计算标志、构建身份、实际传输行数、耗时与 Core profile |

精确 ID GET 仍不宣称多个对象共享快照；现在也在发布答案前验证 schema。样例缓存文件名加入调用身份范围，避免不同身份共用样例路径。

profile 阶段可能嵌套，不把阶段耗时相加当总时间；read_keys/read_bytes 仍为 Core 的逻辑读取计量，不能解释为物理 I/O。`residualEvaluation=true` 也可能仅表示聚合后的别名、排序和窗口处理，需结合 resultKind 判断。

## 明确保留的本地计算

以下边界没有用近似实现替代，也没有标记成已完成下推：

1. SUM/AVG/MIN/MAX：当前 Core 数值聚合可能采用浮点，空集 SUM 为 0；现有 DSL 使用十进制计算，空集 SUM 为 null。保留原实现。
2. 字符串及日期分组、字符串 DISTINCT：Core 会将数字外观字符串归一；日期分组尚不能直接证明与 DSL 的时刻归一一致。保留原实现。
3. 未证明等价的否定、LIKE、部分数值条件、跨变量的 pattern 条件，以及不能证明完整下推的 OR，继续保留本地判断；安全 AND 限制仍可用于减少候选。
4. 多字段排序、HAVING 及有歧义的分组排序/窗口保持原本地语义；不在这些操作之前提前裁剪用户 limit。
5. 同类重复绑定、optional、变长路径等原先不支持的图形仍明确拒绝，没有扩大图查询业务语义。

这些保留项不影响正确读取，但意味着本轮不是所有 SQL/DSL 算子的完整下推交付。进一步能力需求见 [Core 查询语义补充需求](onn-core-t30-query-semantics-requirements.zh-CN.md)。

## 验证

- Adapter 离线回归 108/108；应用装配 1/1。只运行明确选择的测试，没有运行整个外部数据库/模型测试集。
- 108 T30 固定包：原质量数据 20 题与原始期望值逐题一致，并与完整读取后旧 Java 计算逐题、逐行、逐字段一致。
- 新增 3 题聚合对拍：路径计数 127、对象去重计数 31；非空属性计数 21；布尔分组 140/10。均使用 return，结果与旧计算一致。
- 独立 6,001 对象夹具：17 组文本、布尔、空值、时区、数值、OR/AND、分组及窗口语义对拍通过；计数下载 0 对象，精确名称筛选下载 1 对象。
- 108 Workbench → Java 21 Data Engine → 新 adapter → T30：原 20/20 正确；同机 PG adapter 仍有已知布尔条件不支持，剩余 19/19 正确。此问题属于 PG adapter 的执行契约，不能解释成 PostgreSQL 数据库不支持布尔比较。
- 在同一临时 Core 实际复现了数字外观字符串分组合并、浮点累加差异、空集 SUM=0，确认上述本地计算边界有实际依据。

本机使用 JDK 25 编译 release 21；108 完整应用链路实际运行 Java 21。未运行 Core 构建或测试，Core Linux 上游验收与本轮 adapter 验收分开记录。

本次私有证据目录：`~/.codex/artifacts/ontomato-t30-adapter-20261106`。原始业务数据、真实运行配置、凭证和完整响应不进入 Git。

## 本轮应用性能复测

同一份质量输入：29 类、1,979 对象、5,740 边。规模矩阵完成后重建临时 Core，仅导入原始质量输入；计时期间不含 6,001 对象夹具。

共同成功的 19 题，单并发、3 个块、每块每题每后端 3 次预热后取 10 次，共 1,140 次正式样本，全部正确。双方均通过同一个临时 Workbench 和 Java 21 Data Engine 发起。

ONN/PG 中位耗时比的几何平均为 **1.0134**，ONN 更快 10 题，PG 更快 9 题。该数据集本轮满足几何平均不超过 1.5 的目标；复杂图查询仍有明显差距。

| 查询 | ONN 中位 ms | 同机 PG 中位 ms |
|---|---:|---:|
| 客户计数 | 15.231 | 18.920 |
| 产品计数 | 12.703 | 19.784 |
| 日期范围计数 | 15.901 | 19.641 |
| 空值筛选计数 | 18.001 | 19.571 |
| 数值聚合，本地精确计算 | 15.695 | 18.293 |
| 三跳完整关系 | 38.441 | 24.322 |
| 三跳去重分组，本地计算 | 31.399 | 21.889 |
| 三跳质量追溯 | 48.971 | 24.409 |

环境限制：ONN 临时容器限制 2 CPU/3 GiB，PG 使用原共享服务、未限制 CPU；主机仍运行其他应用；双方使用热缓存，不清理共享缓存，ONN 开启 profile。因此这里是该部署条件下的应用对照，不是严格硬件归一的数据库引擎基准，不能推广到百万级或大扇出。

后续完成了 [1～7 跳专项对照测试](onn-core-multihop-benchmark-20261106.zh-CN.md)：双方独立数据容器均限制 2 CPU/3 GiB，覆盖不同关系展开量、筛选起点及明细/计数，共 4,890 次正式样本。高扇出场景仍有明显差距和预算拒绝；手动调整等价 DSL 的遍历起点有明显收益，自动选择起点尚未实现。两轮夹具及运行条件不同，数据应分别理解。

上次 4.34 倍可作为历史参考，两轮发生在不同日期及运行条件下，不能据此宣称一个精确的升级改善百分比。自然语言模型耗时未混入本轮查询计时。
