# ONN Core HTTP 数据读取与图查询功能需求

日期：2026-10-09。接收方：ONN Core 开发团队。

## 1. 背景与交付目标

我们正在为 Ontomato 开发 ONN Core adapter，需要通过 HTTP 读取业务本体、对象和关系，执行图查询与统计，并取得可核验的结果。在开发与测试过程中，发现部分查询行为与 ONN Core v11 使用指南描述的能力存在差距，同时缺少完整分页、跨对象结果绑定等接入能力。因此提出本需求。

交付目标是：**第三方客户端仅根据 ONN Core 发布的接口文档，就能正确读取对象和关系、执行查询与统计，判断结果是否完整，并按调用者权限获得数据。** 文档、实际部署和自动化验收结果应一致。

本文后续只规定 ONN Core 的功能、接口契约和验收条件。接口路径、字段名示例中的“建议”内容可由团队调整，但最终命名和语义必须形成版本化契约。

本轮范围为读取与查询。不要求本轮新增业务写入、Action、向量检索或自然语言问答能力；编辑层仅要求明确读取能力及其启用状态。

## 2. 测试依据与问题性质

测试时间为 2026-10-09，主要服务地址为 `http://192.168.1.108:18081`。只读取元数据、少量 demo 对象以及执行只读查询，没有创建、修改或删除数据。本地参考资料为 `ONN_CORE_V11_USER_AND_TESTING_GUIDE.md`，其中将该端口标为 v11.0.0。

当前 `/ping` 没有构建版本信息，因此尚不能确认部署程序与本地源码完全一致。以下“实测”仅指该服务当时的行为；不能据此认定所有版本都有同样问题。

| 项目 | 使用指南或接入需求 | 实测结果 | 本次要求的性质 |
| --- | --- | --- | --- |
| 多分支深度遍历、条件组 | 指南列为图查询能力 | 两个分支时，`next.where_logic` 和下一层 `next.traverse` 的不可能条件被漏执行，仍返回根对象 | 修正已描述能力，见 R03 |
| 多步 Pipeline | 指南描述复杂多步管道执行 | 第二步使用 `from_step + traverses` 时，遍历和目标过滤没有生效 | 修正已描述能力，见 R03 |
| 投影裁剪 | 指南测试矩阵列出“结果字段投影裁剪” | 只投影 price 时，原始 `data[].attributes` 仍带其他属性；ABC 普通字段与 count 混用时 count 消失 | 明确裁剪范围并修正丢失输出，见 R06 |
| 属性级安全 | 指南承诺按角色自动隐藏受限属性 | 本轮没有可验收的受限字段 fixture；源码检查发现部分路径可能未接入过滤 | 验证承诺及消除风险，未确认线上泄漏，见 R07 |
| 编辑合并和历史 | 指南提供 merged/history 使用流程 | 按实际参数读取返回 503，提示合并引擎/编辑层未启用 | 补齐部署能力声明与启用流程，不直接认定功能未实现，见 R09 |
| 请求校验 | 第三方接入需要明确协议 | ABC 未支持位置的条件被忽略并返回 200；错误 limit 类型则返回 400 | 统一严格校验和文档，见 R01 |
| 完整性与分页 | 全量读取、准确统计需要 | `branch_limit=1` 与 200 得到不同 count，均返回 200，没有截断标识 | 新增完整性与稳定分页契约，见 R02 |
| 跨对象字段绑定 | 关系分析需要同时读取两端字段 | 查询返回叶端对象，源端字段和部分变量 ID 为 null；目标变量条件可能被应用到根对象 | 新增绑定结果能力并修正变量解析，见 R04 |
| 完整邻居与边列表 | 图浏览、关系读取需要 | 现有 `edge-sample` 是抽样，未提供完整邻居分页契约 | 新增读取接口，见 R05 |
| 计数含义、Schema 类型与版本 | 客户端需要确定数据含义 | count 带属性仍计对象数；Schema 存在空类型和空关系端点，两个元数据端点 hash 不同 | 明确契约并补齐校验，见 R06/R08 |

输入格式差异本身不构成缺陷。本需求允许客户端转换成 ONN Core 自己的 DSL；要求服务对不能理解的请求明确拒绝，避免忽略一部分后继续执行。

## 3. 功能需求

### R01：发布可识别的服务版本、能力清单和严格接口契约

**优先级：P0。类型：接口规范补齐及校验修正。**

目前第三方无法从服务确认构建版本、启用功能和支持的 DSL 结构；部分未知字段被忽略，调用者可能得到含义已经改变的成功结果。

要求提供以下功能：

1. 增加版本/能力发现接口，返回程序版本、构建 ID、API/DSL 版本，以及本次部署实际启用的功能。功能列表至少覆盖图查询、Pipeline、绑定结果、稳定分页、快照、属性权限、编辑合并、历史读取。
2. 发布 OpenAPI 和查询请求/响应的 JSON Schema，包含必填字段、类型、枚举、默认值、上限、错误码和返回对象类别。native、Pipeline、ABC 各有独立、准确的示例。
3. 对未知执行字段、不支持的条件位置、变量、操作符及组合返回明确 4xx；错误包含稳定错误码和字段路径。扩展字段如需开放，放入明确声明的扩展区域。
4. 已接收的执行条件必须全部执行。不允许删去无法处理的条件后返回普通成功；服务内部错误也不能转换为“0 条匹配”。
5. 更新指南中的实际请求参数。当前实例点查需要 `class_path + id`，merged/history 使用 `classPath + instanceId`；指南中只传 ID 的示例需要修正，或由服务正式提供并说明兼容行为。指南 8.5 的图查询示例使用 `rootClass`、对象形式的 `where` 和 `traversals`，而 native DTO 使用 `match_class`、条件数组和 `traverse/traverses`；应改成可直接执行的示例，或明确这是另一个兼容协议。

**验收：** 错误拼写、错误类型、未知变量和不支持位置的条件均被明确拒绝；合法请求按文档执行。对于一个不可能匹配的条件，合法表达返回 0 条，不支持的表达返回错误，两者都不能返回匹配对象。版本和能力接口能识别 Edit 未启用的部署。指南示例由自动化测试执行。

### R02：提供结果完整性、稳定分页和一致快照

**优先级：P0。类型：新增契约及错误处理补齐。**

实测同一关系计数请求仅改变 `branch_limit`：设为 1 时 count=1，设为 200 时 count=150。两个响应均为 200，没有说明其中一个参与计算的集合已被截断。`matched_count` 还表示当前页行数，例如当前页 1 条、总体 count=150。

要求提供以下功能：

1. 对对象列表、关系列表和图查询统一返回完整性信息，明确本次执行是否发生扫描限制、分支截断、深度限制、超时、取消、存储读取失败或降级。
2. 分开表达当前页条数、总匹配数和是否还有下一页。无法准确计算总数时，明确标为未知；不能用当前页条数替代总数。
3. 提供稳定 cursor 和确定排序；同一快照分页不能重复或遗漏。仅使用 offset 且底层顺序不稳定，不能作为完整读取协议。
4. 返回数据快照标识及 Schema 版本；后续分页可继续使用同一快照。快照过期或不再可读取时，返回明确错误，不能静默切换到新数据。
5. 聚合必须说明参与计算的输入是否完整。需要精确统计时，输入不完整应失败；允许返回部分结果的模式必须显式声明，并把指标标为非完整计算。

建议响应字段含 `complete`、`truncated_reason`、`page_count`、`total_matched`、`has_more`、`next_cursor`、`snapshot_id` 和 `schema_version`。`has_more=true` 表示还有正常分页，与执行被截断是不同状态，不能混用。

**验收：** 用超过默认/分支上限的数据验证，所有截断都有标识。统计不能把截断集合的 1 描述为全量总数。分页读取的对象集合与同快照全量基准一致；翻页期间修改数据，仍读取原快照或收到明确快照错误。同数替换对象也不能导致未标识的遗漏。

### R03：完整执行多分支、嵌套条件与 Pipeline

**优先级：P0。类型：修正指南已描述的能力。**

当前服务已复现：多分支中的 `where` 能过滤，等价 `where_logic` 却可能被忽略；分支下一层遍历的条件也可能漏执行；Pipeline 从前一步取数据后，`traverses` 没有执行。

要求提供以下功能：

1. 在每一层图查询节点执行该层条件组和下一层遍历；`where` 与等价 `where_logic` 必须得到相同结果。
2. `traverse` 和 `traverses` 均支持嵌套执行。支持深度以内完整执行；超过支持深度时按 R01/R02 报错或声明截断。
3. `from_step` 只负责确定输入集合，后续过滤、遍历、投影和统计仍照常执行。前一步为空时，后一步不能回退为全类扫描。
4. 明确多分支 AND/OR、optional、去重、回环和输出类别的语义。分支数量从一个变为两个时，结果模式不能让客户端靠猜测确定。
5. ABC 的变量条件必须作用于声明变量；目标变量的条件不能被当作根对象的条件执行。

**验收：** 在隔离 fixture 中执行下列用例：

| 用例 | 预期 |
| --- | --- |
| 两个必选分支，目标 `where` 含不可能条件 | 0 条 |
| 上述条件改成等价 `where_logic` | 仍为 0 条 |
| 分支下一跳含不可能条件 | 0 条 |
| 同一遍历单独执行、通过 `from_step` 执行 | 在相同输入和快照下结果相同 |
| 前一步 0 条，后一步引用它 | 0 条，不扫描全类替代 |
| 条件指定目标变量，根对象没有该属性 | 按目标属性过滤 |

此外需覆盖至少两层嵌套、AND/OR、optional 和声明的最大深度边界。

### R04：返回跨对象绑定结果，并保持稳定对象身份

**优先级：P1，完整关系分析必需。类型：新增结果模式及变量解析修正。**

当前遍历主要返回叶端对象，不能同时取得一条匹配中的源对象、目标对象和关系。ABC 声明变量后，源端属性和变量 ID 仍可能为 null。

要求提供以下功能：

1. 新增绑定结果模式。每条结果保留参与同一次匹配的所有对象变量及关系变量；字段投影和过滤按变量解析。
2. 每个对象至少保留 `class_path + id`。系统必须明确 ID 是全局唯一还是类内唯一；类内唯一时，所有缓存、去重、visited 和输出均使用复合身份。
3. 对象身份与同名业务属性分开。例如对象顶层 `id=R:1`、业务属性 `attributes.id=business-1`，两者都能明确读取，不能互相覆盖。
4. 定义重复边、多条路径、回环和去重策略。返回路径匹配行时不能因节点曾出现过而静默删除合法匹配；如只提供可达节点集合，应使用另一明确结果模式。
5. 原有“叶端对象集合”模式可以保留，但文档和响应必须标明模式。

**验收示例：** 隔离 fixture 有一条评价 `R1(rating=5)`，分别关联 `P1(price=10)` 与 `P2(price=20)`。请求源/目标 ID、rating、price 后得到两条绑定行：

| 源对象 | rating | 目标对象 | price |
| --- | --- | --- | --- |
| R1 | 5 | P1 | 10 |
| R1 | 5 | P2 | 20 |

增加目标条件 `price=20` 后只保留第二行。两个类使用相同 ID、ID 含冒号或 Unicode、对象带同名业务属性时，身份仍可无损读取。两条不同边不得被错误合并；回环按明确模式返回或明确拒绝。

### R05：提供完整邻居和关系边列表 API

**优先级：P1，完整图浏览必需。类型：新增 HTTP 读取能力。**

现有 `edge-sample` 只能取关系样本，没有完整性、稳定边身份和完整分页，不能用于回答“某对象有哪些关联对象”。

要求新增接口，接收源对象类路径、ID、可选关系路径和方向（出边、入边、双向），返回：

- 邻居对象的类路径与 ID；对象属性是否展开、展开字段的选择方式需要明确。
- 每条边的稳定身份、关系路径、源/目标对象的完整身份及关系属性。
- R02 规定的分页、快照和完整性信息。
- 对反向读取、双向关系、多条同端点边和无邻居对象的确定语义。

建议接口为 `GET /api/v1/data/neighbors`，具体命名由团队确定。身份字段必须结构化传递，不通过未转义的冒号拼接和拆分恢复身份。

**验收：** 对一个含入边、出边、两种关系和多条同端点边的对象，分别验证方向与关系过滤。每页 2 条拼接后与完整基准集合一致；每条边身份稳定、关系属性正确。带冒号 ID 无损。无邻居返回完整空集合；读取失败返回错误。

### R06：定义准确的聚合与字段投影语义

**优先级：P1。类型：统计契约补齐及输出修正。**

实测 `/demo/user` 有 108 个对象，一些字段存在缺失；`count(status)`、`count(marker)` 和对象 count 均为 108。指南没有明确区分“对象数”与“属性非空数”，因此本项要求补齐语义，不能仅凭这次测试认定现有 count 违反已经发布的定义。

同时，ABC 普通字段与 count 混用时，响应只保留普通字段；native 只要求 price 投影时，原始数据仍包含其他属性。

要求提供以下功能：

1. 分别提供对象数、属性非空数、属性去重数；文档说明 missing/null、空集合、数值类型和重复路径如何参与计算。现有 count 可保留兼容语义，但需明确命名及新操作。
2. 去重保持类型信息：数字 `1` 与文本 `"1"` 不因字符串化被合并。布尔、数值、字符串与 null 的规则明确。
3. 明确 sum/avg/min/max、GROUP BY/HAVING、聚合排序的处理顺序及支持范围；不支持的组合明确拒绝。
4. 合法的字段与聚合混合请求保留全部输出；不合法的组合报错，不能只执行其中一部分。
5. 提供明确的响应字段选择机制。要求裁剪后，所有返回容器都不再附带未选择的业务属性；如果 raw data 是独立的可选结果，必须显式选择才能返回。
6. 投影与访问控制分别生效。选择某字段不代表有权读取该字段；未选择字段也不能通过原始数据旁路返回。

**验收：** 四个对象的 `x` 分别为缺失、null、数值 `1`、文本 `"1"`：对象数为 4，非空属性数为 2；采用排除 null/missing 的属性去重定义时为 2。若类型 Schema 禁止混合值，写入明确拒绝，并用符合最终类型契约的 fixture 验证去重。合法投影与聚合均返回；只选择 price 的响应不带其他业务属性。准确聚合满足 R02。

### R07：在所有读取与计算入口统一权限和属性保护

**优先级：P0，生产使用前必验。类型：验证指南已承诺能力并消除源码风险。**

指南承诺受限字段按角色隐藏。此次只读测试没有准备可控的安全 fixture，**尚未证实线上存在保密字段泄漏，也没有完成权限能力验收**。源码审查发现部分读取/查询路径可能未应用统一过滤，需要团队验证并修正。

要求提供以下功能：

1. 明确 HTTP 客户端身份认证方案和受信角色来源。角色头若由网关注入，明确网关清洗及服务信任边界；不能允许普通客户端声明 admin 就取得管理权限。
2. 实例 GET、sample、shape/values、邻居/边列表、native、Pipeline、ABC、MCP 等入口采用一致的类、关系和属性规则。每一步、每一个关联类均检查权限。
3. 同时保护原始数据、投影、指标和历史视图。无权字段不能通过过滤、排序、聚合或错误详情被推断；无权操作明确拒绝或采用事先定义的安全语义。
4. 权限依赖的 Schema/策略读取失败或安全标记无法识别时，不能自动按公开字段放行。
5. 能力发现接口明确本次部署是否启用了认证、资源授权和属性过滤。

**验收：** 团队提供公开字段和受限 cost 字段，以及 reader、finance、无身份、无权限等调用凭据。reader 无法通过任何输出容器读取 cost，也不能绕过过滤/统计推断；finance 能在授权范围读取。第二步或目标类越权被拦截。普通调用者伪造角色失败；Schema/策略异常不会放行。测试只在隔离环境执行。

### R08：提供可确定解释的 Schema、继承和变更版本

**优先级：P1。类型：模型契约补齐及数据质量修正。**

实测 Schema 有 55 个空类型属性、26 个其他非基础类型属性、13 条没有两端类的关系。`schema/all` 与 `schema/meta` 的 hash 不同。缺失类型和 hash 差异需要说明；不能直接判定所有非基础类型无效，或据此判断 Schema 发生变化。

要求提供以下功能：

1. 发布完整类型表，明确别名、json/vector/derived、null/missing、日期时区及继承属性的编码规则。扩展类型给出语义和能力标识。
2. 空类型属性、无端点关系若是合法的草稿/抽象定义，输出明确状态和不可执行原因；若是已发布可查询定义，补齐类型和端点。实例含未声明字段时，明确允许范围及权限处理。
3. 定义 `parentPath`、属性继承、override、父类查询是否包括后代及身份去重。缺失父类、继承环、冲突定义应报错。
4. 提供一致可用的 Schema 版本/fingerprint。不同 hash 如各有用途，明确算法、输入范围和比较规则；两个端点比较同一用途时应一致。
5. Schema 全量读取本身具备一致版本；客户端可在查询时指定/校验版本，映射变化后明确失败，避免沿用过期字段含义。

**验收：** 所有已发布可查询定义均能依据契约解析；草稿/抽象定义可被明确识别。继承 fixture 的有效属性、覆盖规则和父类结果与文档一致。无变更时同用途 fingerprint 稳定，变更后版本改变；使用旧版本执行收到明确错误。

### R09：明确 Base、Merged 和历史读取的可用性

**优先级：P1；若当前交付只包含 BASE，应先按 R01 声明限制。类型：部署补齐及视图契约明确。**

实测 merged/history 返回 503，分别提示合并引擎、编辑层未启用。这说明当前部署不可用，不能直接推断编辑层代码不存在。

要求提供以下功能：

1. 交付可复现的启用配置和部署步骤；若本次不交付编辑层，在能力接口和指南中明确说明。
2. 标明普通 GET、图查询和 Pipeline 默认读取 BASE 还是 MERGED；允许客户端明确选择已支持视图，并在响应中回传视图。
3. 同一视图、快照下，点查与列表/查询对覆盖字段、软删除和历史状态的处理一致。选择不支持的视图明确失败，不能回退到 BASE。
4. 历史和时间点读取使用稳定对象身份和确定时间规则，并满足同等权限保护。

**验收：** 未启用部署的能力接口明确标 false，调用对应视图返回可识别错误。已启用隔离部署中，团队准备覆盖、删除、历史 fixture；点查和查询的 MERGED 结果一致，BASE 可区分，历史状态可核验。只读验证人员不需要自行修改生产数据。

### R10：交付可复现的接口验收包

**优先级：随 R01—R09 一同交付。类型：验收交付要求。**

团队应提供一个独立隔离的测试实例和小型固定数据集，包含：

- 一对多关系、多分支、两层遍历、optional、重复边、回环。
- 两类相同 ID、带冒号/Unicode 的 ID、同名业务 id 属性。
- 缺失/null、分组字段、聚合样本、继承与 Schema 变更样本。
- 超过分页/分支限制的数据，以及超时/读取失败/快照失效场景。
- 不同权限的字段和凭据；启用编辑层时的覆盖、删除、历史样本。

验收包包括：构建版本、启用配置、OpenAPI/JSON Schema、fixture 创建说明、请求文件、预期响应、可一键运行的测试脚本和实际通过报告。创建 fixture 由团队在隔离环境执行；对已有测试/生产服务的验证脚本保持只读。

所有指南 curl 示例均纳入自动化验证。测试必须断言字段值、对象集合和完整性状态，不能只断言 HTTP 200。未支持能力列出限制，不计为“全部功能通过”。

## 4. 交付顺序与完成标准

| 批次 | 必须交付的结果 | 对应需求 |
| --- | --- | --- |
| 第一批：可信查询基础 | 能识别部署版本与能力；请求无静默忽略；递归与 Pipeline 按请求执行；不完整结果可识别；权限能力经隔离测试确认 | R01、R02、R03、R07，配套 R10 |
| 第二批：完整关系读取与分析 | 跨对象绑定、完整邻居分页、稳定身份、准确统计与裁剪、可解释 Schema | R04、R05、R06、R08，配套 R10 |
| 第三批：编辑视图读取 | 明确启用状态和默认视图；已启用时一致读取覆盖、删除与历史 | R09，配套 R10 |

每项完成标准：接口已在交付版本实现，文档与能力声明同步，对应验收用例通过，返回结果能确认版本、视图及完整性。功能依赖配置的，必须同时交付配置和部署验收结果。

请按 R01—R10 逐项提供：当前版本是否支持、实际接口和语义、需要修复还是新增、计划交付版本、验收结果。对本报告实测行为如认为属于既定设计，请说明正式契约及客户端获取完整结果的方式；涉及统计输入截断、条件遗漏和权限的限制必须能被客户端识别。
