## 三、剩余问题统一清单

### B1 / R1：类型冲突只在解析时拒绝，保存前与后代校验未落地（P1）

现有角色层间 AND、层内 OR、admin-only 的固定反例已通过，认可该部分修复。

但以 admin 经真实 router 调用 `POST /api/v1/schema/ontology`：

- 已有父类 `salary:float`，新增子类 `salary:string`：返回 **201**，非法子类已落库。
- 父类原先无 salary、已有子类 `salary:string`，向父类新增 `salary:float`：返回 **201**，造成子类继承冲突。此例是新增字段，不依赖 `force=true`。

两条均要求 4xx 且持久化状态不变，实际均失败。旧用例接受“保存失败 **或** 有效解析失败”，所以 62 条转绿不能证明团队宣称的“保存/解析双重拒绝”。

代码位置：`internal/domain/schema_repo.go:24` 的 `SaveOntologyClass` 没有调用继承校验；`internal/domain/effective_policy.go:134` 的辅助方法未接入保存路径；`internal/api/handlers.go:741` 直接保存。

**要求：**对候选 Schema 及受影响后代先校验再提交，错误类型稳定；新增冲突与父修改反例一并作为固定回归。已有非法 Schema 解析时继续 fail-closed。

证据：`schema_write/new_child_conflict`、`schema_write/parent_update_conflict`。

### B2 / R2：歧义边仍会误删、误读，不存在的边也可能返回成功（误删 P0，其余 P1）

保留原冲突：旧边 `a → b:c` 与 V2 边 `a:b → c` 共享同一个旧出边 key。

| 场景 | 实际 |
|---|---|
| 两条边都没有属性，删除 V2 边 | 返回 nil、WriteBatch=1、另一条旧边被删除 |
| 属性不同，删除 V2 边 | 保留另一条旧边，但仍修改 V2 且返回成功；未满足冲突零写 |
| 没有 V2 副本，删除含歧义身份的边 | 返回 nil，歧义旧记录被删除 |
| 删除时旧边 Get 注入真实存储故障 | 故障被跳过，仍删除 V2 并返回成功 |
| 旧边为 `a:b → c`，查询 a 的单条/批量邻居及样本 | 错造出 `a → c` |
| V2 与旧格式都不存在，GetEdge | 返回非空 Edge 与 nil error |

根因：`internal/domain/graph.go:87–102` 用属性字节是否相等判断身份。**内容相同不证明属于同一条边，空属性尤其常见。** `edge_dual_scan.go:145–147、165–167` 仍取首末段猜身份；`graph.go:168–172` 抑制最终 not-found 后继续构造边。

**要求：**歧义旧记录必须靠无歧义编码或显式确认映射处理；不确定时返回冲突且所有 key 零写。真实 Get 故障不得当 not-found。单条/批量/样本/推理统一使用相同解码规则；真正不存在返回 not-found。

本组共 8 条补测失败；其中删除故障同时属于 R3 错误传播边界。仓储测试直接断言 error 与 WriteBatch=0，尚未把该错误的 HTTP 409 映射算作已测试通过。

### B3 / R3：时间窗读取故障仍返回 200 exact 空集（P1）

对存在且日期在窗口内的对象，在 V2 属性 Get 注入真实存储错误：Native、Pipeline root、from_step 均返回 **200 + data=[] + total_exact=true**。

`internal/domain/executor.go:3203` 的 `filterIDsByTemporalWindow` 仍只返回 ID 列表；批读失败后退到逐条检查，逐条错误又被忽略。普通 where 已修复，时间窗没有同步贯通。

**要求：**时间窗助手及全部调用点返回/传播 error，保留 cause 与错误分类。依赖故障给相应 5xx，不能作为“不匹配”。保持三入口正反向测试。

证据：`temporal_read_fault/native|pipeline|from`，3 条失败。故障注入仅运行于独立测试进程，未对 108 实库注入故障。

### B4 / R4：where 在 top_k 后才执行，真实数据会漏结果（P1）

三个对象：v0(age=10, vector=[1,0])、v1(20,[1,1])、v2(30,[0,1])。查询 `age>=20`、query=[1,0]、top_k=1。

正确：先筛出 v1/v2，再选择 v1；source=2、total=2、window=1。

- Native 与 Pipeline root：先取 v0，再按 age 排除，返回空集，仍声称 total=3、window=1、has_more=true。
- from_step：返回 v1，阶段计数 2/2/1，作为正向对照通过。

**108 同一候选版本上已复现相同结果**，不是仅存在于测试 stub。

根因：`internal/domain/executor.go:2245–2275` 先全类 rerank/top_k，后执行 where/where_logic。

**要求：**三入口共用方案已冻结的阶段顺序：种子/授权/非向量过滤 → 评分/阈值 → top_k → 展示排序/分页。补入 where/where_logic/时间窗与向量的组合测试，不能仅修计数字段。

### B5 / R6：迁移工具已新增，但恢复与回滚安全仍不达标（数据损失相关 P0）

本轮 6 条迁移安全反例均失败：

| 反例 | 实际后果 | 必须满足 |
|---|---|---|
| dry-run 后目标新增不同 V2 值，再 apply 旧计划 | V2 的 NEW 被 OLD 覆盖，旧 key 被删，无错误 | 提交前验证源/目标 preimage，冲突零写 |
| checkpoint 后源值变化、key 未变 | Resume 接受并迁移 | 验证源快照/内容，过期计划拒绝 |
| A 库 checkpoint 用于 B 库，同 key 不同值 | Load/Resume 接受并改写 B | 校验数据库/源快照身份，错库拒绝 |
| 130 字节 classPath 的报告 JSON 往返 | 二进制 target key 变化；apply 删除旧 key，正确 V2 key 不存在 | key 用无损编码，验证序列化往返及目标合法性 |
| 备份数据文件被截断为空后 rollback | 返回成功、restored=0，当前业务记录被清空 | 破坏性操作前核验 manifest/数量/哈希与完整性 |
| 声称全库备份，含 schema/index/data 后回滚 | 仅 data 恢复；schema/index 仍为修改后值 | 完整备份恢复；或明确限定范围并给出一致性重建闭环 |

代码依据：`migration.go:241–251` 未重验目标；`:296–321` 不验证已保存的 SourceSnapshot；`:407–419` 计划哈希只含 key 映射，不含内容；`:47` 用 string 存二进制 key；`:355–402` 不读 manifest，先清空再重放；`:423–430` 仅覆盖对象/边 key。

另有代码/团队测试直接可见的交付差距：

- `TestMigrationInterruptResume` 把“部分提交后 Resume 拒绝，再重新 dry-run/apply”作为通过条件。**这不等于承诺的 checkpoint 原子进度恢复**：实体镜像/属性与 checkpoint 没有共同提交边界，也没有逐步 durable journal。
- `classifyByV2` 和 `applyOne` 把任意 Get 错误当作不存在/幂等跳过，尚未保留 R3 的错误分类。
- backup 注释称 base64 JSON lines，实际写 `%q\t%q`；manifest 只有 count。不能视作已交付物理 SHA/逻辑校验闭环。
- 在本次检索范围内未定位到独立、可操作的迁移/恢复/回滚手册及完整交付索引。T7 把源码注释和测试称作手册，不足以支撑操作者安全执行。

**要求：**先修数据损失反例，再完成原 R6 原子进度恢复、无损计划格式、备份完整性验证及操作手册；同一隔离持久化库做提交前后中断、关库重开、镜像/内容哈希校验和回滚。以上不要求生产迁移、生产 IdP 或持久化 HNSW。
