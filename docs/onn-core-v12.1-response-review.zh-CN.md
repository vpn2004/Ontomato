Q01 表明“无遍历时精确”目前并不成立。V12.1 修复了 `where_logic` 路径，但普通 `where` 仍受分页候选窗口提前限制。Q03/Q04 与安全 S01/S02 共享提前返回路径。Q08 表明只在顶层记录截断不够，嵌套阶段也必须向最终结果传播。

**要求与完成标准：** 普通 where、where_logic、无条件、排序、指标、Pipeline 等路径统一生成完整性信息；page_count 与实际当前页一致，total 表示契约约定的总集合，has_more 不得把第一页误报为最后一页，任意层级发生执行截断都必须显式报告。以上场景与原始用例同时通过。

关于图查询计数，可以暂不要求每次执行昂贵的全图精确 count，但必须区分：

- `source_candidate_count`：源候选数量；
- `total_matched`：当前输出结果集合总数；未知时返回 null，或以明确的 `total_exact/count_kind` 标示；
- `has_more`：实际输出集合是否仍有正常下一页；
- `truncated`：执行阶段是否丢弃了本应参与结果或统计的数据。

字段名可由团队确定，含义必须稳定。当前“有遍历时为源候选数、只保证不虚报 0”的说明不能用于准确统计；源码不同路径也未统一为源候选数。不能将源候选、叶端结果、分页条数放入同一无标识字段。

## 8. 验收脚本与接入侧注意事项

团队 19 项脚本确实通过，但当前覆盖不足：fixture 写入没有逐次检查 HTTP 状态；个别“没有某字段”的文本检查可能将错误响应误判为成功；不可能条件只取缺省 `data=[]` 也可能掩盖错误；授权正例主要检查 200，尚未断言正确聚合值。应改为“状态 + 响应结构 + 值/集合 + 完整性”联合断言，并覆盖排序/指标、嵌套分支、ABC 和旁路端点。仓库中已有条件正例，应保留，无需重新从零建立。
