- 诊断在响应到达后发生，不是执行前拦截，也不更改原响应或证明查询语义正确。引擎的既有验证仍负责拒绝非法查询；若 Harness 不返回 DSL，客户端无法诊断其内部重试。执行前有限修复、Java 通知唤醒和持久化后台质检仍是后续工作。

### 慢样本与下一轮重点

正式环境的跨关系题首数据等待约 99.06 秒，主答案约 110.60 秒完成，连接约 152.61 秒结束。引擎同一 session 记录了 13 次失败工具请求：11 次 `missing properties predicate`，1 次关系名称不可识别，1 次关系端点/方向不匹配。首尾拒绝间隔约 54.52 秒，期间包含模型思考与工具往返，不能把这个区间算作数据库执行时间，也不能将每次拒绝等同一次真实 ONN 数据读取。

同题旁路主答案约 44.45 秒、连接约 95.39 秒。两次明显不同，证明性能仍不稳定；本轮仅增加观测，没有减少模型调用或修复后端重试策略，不能将其中较快的样本当作提速成果。六个响应的显式 DSL 均未提供，诊断正确记录 unavailable，不能从客户端声称“已拦截这些 13 次错误”。

下一轮优先顺序：

1. 在 Ontomato 引擎的 DSL 工具入口补结构诊断与精确 JSON 路径、关系全路径/方向提示，区分不可重试结构错误和可重试运行故障；对重复无效计划及总修复次数设预算。超过预算明确失败，不忽略过滤或伪造答案。先复现这 13 次拒绝并验证合法图查询、无过滤对象、权限和完整性语义。
2. 为 Java Harness 的模型/工具/队列发送补充关联跨度，替换现有一秒 Future 等待加十秒 sleep；保留取消、完成唤醒、消息顺序和清理测试。客户端后端流日志只能定位大段，不能单独证明其中数据库、模型和固定等待各占多少。
3. 确定字段优先从本体和 outKeyRefs 生成展示计划，减少本次约 1–4 秒的展示模型调用。
4. 按已定方案实现持久化后台质检及 UI 按轮次更新，验证管理 PG 事务、租约、恢复和连续提问。当前主答案完成后到连接结束仍有约 14–51 秒收尾；该差值含质检和传输，不是纯质检 CPU 时间。

这些工作主要落在 Ontomato 的引擎、Workbench 和 UI；本轮没有证据要求先升级 ONN Core 才能减少重复试错。
