# T33 上线后：质量追溯环境与 PostgreSQL 实测对比

日期：2026-11-09。使用 108 已部署的质量追溯数据和 T33 产物，重新通过 Ontomato 比较 ONN Core、同机 PostgreSQL 和远程 PostgreSQL。全部测试完成，临时应用及其两个元数据库已清理，3010/3011 保持原配置。本次未修改任何本地 `onn-core` 目录文件。

## 结论

当前 ONN 可以承载这套质量追溯业务数据，已经在部分查询上取得应用响应时间优势，但尚不能说全面超过 PostgreSQL。

- 正确性：ONN 62/62；同机 PG 和远程 PG 各 61/62。PG 的唯一失败是 Ontomato `PostgreAdapter` 拒绝布尔字段等值条件，不是 PostgreSQL 数据库不支持。原生 SQL 在两个 PG 上均正确返回 10。
- 61 道共同通过的查询，每后端每题 30 次正式样本，共 5,490 次；全部答案正确、0 计时失败。ONN 在 47 道更快、14 道更慢；逐题中位耗时比的几何平均为 **0.827**，相对同机 PG 约低 **17.3%**。
- 优势主要在对象计数、ID 查找、部分过滤聚合及关系路径计数。1–7 跳完整计数全部快于同机 PG，逐题耗时比的几何平均为 **0.825**。
- 关系明细仍有差距：1–7 跳明细的逐题耗时比几何平均为 **1.166**，ONN 约慢 **16.6%**；最慢的业务三跳明细为 **35.650 / 20.629 ms**，ONN 约慢 **72.8%**。
- 混合并发 16 时吞吐 **117.8 / 116.2 req/s**，p95 **222.0 / 218.9 ms**，两边接近；并发 4、8 时 PG 吞吐更高。
- 额外复测物化模式后，七跳明细仍为 **39.794 / 33.662 ms**，最慢业务三跳仍为 **36.665 / 22.339 ms**。现有差距不能只归因于窗口模式。

总计 **9,710 次正式计时请求**：基础 5,490、混合并发 3,200、物化诊断 1,020，均通过各自独立答案校验，0 计时失败。预热、数据回读、正确性预检和生产入口前后检查不包含在这个总数中。

因此这是**实际部署下的 Ontomato 应用链路比较**，包含 SQL 规划、HTTP、JDBC、权限处理、对象转换和 JSON 结果传输，不是硬件隔离的纯数据库引擎基准。不含 LLM 生成时间，也没有用两个模型分别生成不同 SQL 来比较。

### 查询与采样

62 道题包含原有 20 道业务查询，以及 42 道 1–7 跳专项查询。每个跳数分别覆盖明细、完整计数、起点筛选计数、终点筛选计数、从筛选终点反向起步的等价计数、终点去重计数。

双方使用相同问题和等价 DSL，仅替换类路径和 adapter 所需的关系键表示。PG 本体的关系通过已经全量核实的 FK 字段连接，不能把 ONN 显式边与不等价连接进行计时。

正式单并发采用 3 块采样，每块每题每后端 3 次预热、10 次正式，共 30 次；块内题序固定随机化，块间后端顺序轮换。每次正式返回都与独立对象/边夹具期望值校验。未指定排序的明细按完整多重集比较，保留路径重复；排序/分页题按顺序校验。没有只校验行数就判定正确。

1–7 跳链路：供应商 ← 批次 ← 装配 → 产品 ← 检验 ← 检验结果 → 检验项 → 检验计划。完整路径数依次为 106、94、94、63、128、128、128；所有明细均在 5,000 行请求范围内完整返回。该数据无法证明百万级对象、高扇出大明细、环或变长路径的性能，也未重新测试 6/7 跳合成大窗口。

### 阶段证据和 PG 计划诊断

主测试窗口模式中，最慢三跳业务明细返回 191 行，adapter `remoteRead` 中位约 25.46 ms、残余计算约 1.30 ms，Core `evaluate` 中位约 17.16 ms；七跳明细对应约 28.23、1.62、15.57 ms。阶段包含嵌套及不同请求步骤，不能相加成完整 HTTP 时间。证据说明远程读取/计算仍值得优先分析，不能仅靠本地聚合优化解释差距，也不能只凭 profile 宣称已经找到全部根因。

所有计时结束后，用 PG adapter 实际返回的 SQL 做 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`，每题 5 次，不改全局/会话规划参数。该诊断与应用 HTTP 耗时分开：

| SQL | 规划中位 ms | 执行中位 ms |
|---|---:|---:|
| 七跳完整计数 | 13.256 | 0.975 |
| 七跳明细 | 12.590 | 0.997 |
| 最慢业务三跳明细 | 2.537 | 0.548 |

PG 七跳应用请求包含明显规划成本；ONN 七跳计数比 PG 快，不等于 ONN 的纯计算时间比 PG 更低。PG 默认 `join_collapse_limit=8`、`geqo_threshold=12`、`jit=on` 均保留。

## 后续安排建议

1. **ONN Core 与 adapter 优先复现上述 191 行三跳明细**，固定相同普通读角色、查询 DSL、源版本和数据，拆分 Core evaluate、字段权限/编码、HTTP 往返及对象转换。目标应是降低明细成本；不能只用计数较快来关闭明细性能问题。
2. **复测中等并发的明细混合负载**。本次并发 4、8 的吞吐和 p95 落后，在现有应用链路中仍存在；需要阶段级并发证据后再决定 Core 元数据锁、权限表示、应用连接或结果编码的优化归属，不能预先归咎于单一组件。
3. **Ontomato 修复 PG adapter 的布尔等值执行契约**，保留 boolean 类型与 null 语义后加入定向回归。这是应用侧问题，不应要求 ONN 团队修复 PostgreSQL。
4. 在这套小数据明细性能稳定后，再单独扩大对象数、关系扇出和持续并发；T33 团队原隔离大窗口成绩和本轮真实部署成绩分开保存。当前无需重新部署 Core 来完成这次测试，也没有新发现的正确性阻塞。

本次不据此修改生产查询语义或自动选择模式，3011 继续保留已经部署的窗口配置。当前 5/6 跳明细在本轮略超 ONN/PG≤1.3 的历史目标，最慢业务三跳超过更明显；旧隔离验收通过不能替代当前普通角色和实际部署的对照成绩。两轮运行环境不同，本报告也不把它直接判为 T33 相对 T32 的版本回退。
