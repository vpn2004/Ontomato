# Ontomato 问数时延优化：方案与小规模试验

日期：2026-11-12。先验证设计和边界，再按验收关口进入正式实现与 108 灰度。当前线上基准：主答案约 55 秒、质检等待约 60 秒、整条连接约 115 秒；本题七次成功数据读取合计约 0.10 秒。

## 分阶段方案

1. 统一观测 firstDataMs、answerReadyMs、qualityFinishedMs、streamClosedMs；按 traceId 关联模型、工具、Java、Node、ONN。保留原始答案正确性基准。
2. 质检由独立持久化任务承接，答案提交与质检入队保持原子性；身份键包含 domain/user/thread/request/stage，任务具有租约、重试上限、幂等提交、取消和重启恢复。主回答完成后释放输入，质检单独更新对应旧消息，不能覆盖下一轮回答。确定性权限、完整性校验仍在发布前完成。
3. Agent 消息改为可唤醒等待，收到数据或完成信号立即发送；先保留现有权限与工作区归属，验证并发、取消、终止与清理。质检状态禁止连续 SELECT，改成事件通知或有界轮询，并管理 executor 生命周期。
4. DSL 输出在读取业务数据前结构校验，明确 properties 的对象类型及 JSON 路径。仅回传必要错误；同一无效计划不反复执行；最多一次受控修复，再明确失败。禁止忽略筛选或把截断数据当全量。
5. 字段显示优先采用本体/outKeyRefs 的名称、类型和单位；未映射派生字段才调用模型。简单计数/关系读取优先结构化执行，复杂计算才使用 Python；不能绕过既有权限、版本和来源证据。
6. 后台质检描述可在并发上限内合并或并行，质检与指标模板生成分开。修复 embedding 配置前按不可用能力明确处理，不能伪造质检通过。

## 本轮隔离试验与闸门

- A：对真实 late-fact 模块做假时钟测试，核对当前 60 秒等待、超时、取消、失败及结果写回；验证不能只删 await。
- B：持久化质检任务原型，验证答案先完成、任务重启恢复、身份隔离、租约防旧 worker 回写、取消和失败状态。原型使用独立本地测试库，不连接线上业务库；通过仅代表状态机设计可行，不能替代 PostgreSQL 事务及 UI 集成验收。
- C：事件等待微实验，核对即时唤醒、消息有序不丢失、完成唤醒、取消与并发；仅报告机制耗时，不将其当真实问数提速。
- D：真实 ONN DSL 编译器离线回放，验证合法查询保持语义，错误过滤结构在数据读取前拒绝。通过不等于模型首轮成功率提升，后者需要同一模型多轮 A/B。

以上隔离试验全部通过后，才将对应方案纳入正式实现。108 部署的额外关口：Java/Node/UI 定向测试通过、权限/取消/刷新/重连/跨轮质检通过、管理 PG 任务的崩溃恢复通过，并在质量追溯临时实例串行完成三类问题的至少三轮比对。任一必需关口未完成或失败，都不切换现有 3011/3010。

## 灰度与回滚

优先在质量追溯旁路实例验证，新的质检协议必须由前端、Workbench 和引擎协同开启。以功能开关保留现有等待模式；开关回退后仍接管已经持久化的任务，不删除任务表或抛弃结果。首轮通过后只灰度质量追溯，再考虑物流。

建议灰度目标：答案结果和证据全量一致；语法失败不重复提交；已知结果的推送额外等待 p95 < 500ms；质检超时不阻塞下一问；主回答完成时间和质检时间独立展示。模型端时延与首轮 DSL 成功率按串行多轮中位数/高分位验收，不承诺本轮原型就达到某个真实问数秒数。

## 研究与试验结果

本轮结论：设计层面小试通过，可以据此分阶段实施；正式应用的上线关口尚未通过，当前 108 不切换。以下区分真实产品模块测试与独立原型，不能把这些数字汇总成“线上端到端测试通过”。

| 试验 | 结果 | 能说明什么 |
|---|---|---|
| 真实 late-fact 模块，依赖 mock、假时钟 | 7/7 | 60 秒边界、完成写回、调用方取消、已取消入口、失败状态、写回异常和 pending 所有权符合当前行为 |
| 持久化质检状态机，独立 SQLite | 12/12 | 答案/任务原子提交、答案先可读、租户/用户/轮次隔离、四 worker 竞争、真实子进程退出后重启认领、过期租约拒绝写回、幂等完成、取消、三次重试上限通过 |
| Java 队列通知原型 | 6/6，4 个生产者共 2000 条消息 | 有序、无丢失/重复、容量限制、完成唤醒、取消、定时等待通过 |
| 实际 ONN 编译器离线回放 | 66/66 | 62 个既有合法查询编译及输入不变、3 个错误过滤结构拒绝、1 个重复关系路径的真实去重求值通过 |

Java 队列微实验：同样在队列轮询开始后约 100ms 放入消息，现有“1 秒 Future 等待 + 10 秒休眠”机制的一次等待约 10906.49ms；通知机制 30 次样本的 p50 为 0.0453ms、p95 为 0.1197ms。这是本机 JDK 队列唤醒耗时，旧机制单次样本刻意落在不利的轮询相位，不是旧机制 p95，也不是 Java 完整服务或模型问数的加速比例。只能说明固定等待可以消除。

late-fact 测试首次运行的两个失败来自试验未安装 Workbench i18n 宿主；补齐测试依赖 mock 后 7/7 通过，产品代码未为此修改。质检状态机的 PostgreSQL SQL/事务语义、真实 UI 更新及多节点部署尚未验证；SQLite 测试通过不能替代这些关口。当前没有新一轮真实模型 A/B，不能声称模型语法成功率或 55 秒主回答时间已经改善。

## GitHub 参考与可借鉴点

已读取具体文件，不仅查看项目简介。本次查到的 Ontomato 上游主线中，ABCHarnessServiceImpl、CheckController、late-fact.ts 三个相关文件与本地内容完全一致，所以直接更新上游不能解决本轮已定位的问题。未 fetch、合并或切换任何 Git 分支。

1. **Instructor：结构校验、有限修复、重试预算。** [校验与纠错](https://github.com/567-labs/instructor/blob/aeb7e2558166caeec497e541bcfc6b4eaa2cf53b/docs/concepts/reask_validation.md)、[重试与超时](https://github.com/567-labs/instructor/blob/aeb7e2558166caeec497e541bcfc6b4eaa2cf53b/docs/concepts/retrying.md)。可借鉴精确字段错误以及分别计数 SDK 网络重试和模型修复轮次。我们使用现有 Java/TS 机制实现，不为此引入 Python 运行依赖。一次模型失败可能在 SDK 内重试多次，不能只限制 Agent 轮数；总时间、输出 token 和修复次数要分别有预算。
2. **LangGraph：取消与超时后的写入约束。** [任务重试与超时实现](https://github.com/langchain-ai/langgraph/blob/b4cb0f19e3d8984e8a57f85667b8d1bec018f0ab/libs/langgraph/langgraph/pregel/_retry.py)。它区分 run/idle timeout，并对超时后的写入施加边界。质检任务应以租约世代/状态条件更新防止旧 worker 晚到覆盖新结果；取消等待不能被误认为远端模型已停止。本次参考为 Python 上游实现，不能假定本地 JS LangGraph 1.2.6 具有完全相同 API。
3. **OpenAI Agents：逐次 span 和有限并行。** [追踪](https://github.com/openai/openai-agents-python/blob/64fbde5d02b42ae5f9db668eb0184cdb3fc9d775/docs/tracing.md)、[并行示例](https://github.com/openai/openai-agents-python/blob/64fbde5d02b42ae5f9db668eb0184cdb3fc9d775/examples/agent_patterns/parallelization.py)。借鉴每个模型/工具都有起止时间、统一 trace 的做法；两个独立程序说明可限流并行，最终评审仍依赖它们的结果。不会照搬同时问多个 Agent 再投票，这会增加成本，并非本题需要。追踪接入现有诊断日志，不自动启用第三方 trace 上传。
4. **执行前检查与事后评审分开。** [Guardrails 边界](https://github.com/openai/openai-agents-python/blob/64fbde5d02b42ae5f9db668eb0184cdb3fc9d775/docs/guardrails.md)说明阻塞检查和并行检查的差别。权限、租户、过滤与结果完整性属于必须先完成的确定性检查；可后置的是业务解释质量评审。不能为了减小等待把所有检查后台化。

## 正式实施拆分

| 轮次 | 改造位置 | 放行条件 |
|---|---|---|
| 第 1 轮：可观测、通知、有限轮询、DSL 诊断 | engine ABCHarnessTaskService/ABCHarnessServiceImpl/CheckController；adapter 编译入口；现有诊断日志 | Java 定向取消/结束/乱序/清理测试；同样错误不会读取数据或反复提交；合法数据/权限语义不变 |
| 第 2 轮：质检任务独立于回答完成 | contracts 的任务状态；管理 PG 持久化与迁移；Node query-run/late-fact/chat；UI 标准流及历史更新；Java 质检任务接口 | PG 原子提交/并发认领/租约及重启恢复，UI 连续提问/刷新/断线恢复/切换账户隔离，答案就绪与质检就绪分别展示 |
| 第 3 轮：减少模型调用 | 字段展示计划、结构化查询路径、质检程序说明；模型按职责配置 | 同一模型配置下的串行多轮 A/B，正确性不下降，首轮成功率和答案完成时间可重复改善 |

第 1 轮先进行，可以减少无效等待和试错；第 2 轮解除约 60 秒的收尾等待；第 3 轮再压缩约 55 秒的主链路。每轮独立可回退，不把三个方向一次性打包上线。

持久化方案优先复用已有 query_runs 与管理 PG 基础设施；已存在的分析任务运行器可以复用身份、状态和事件设计，但质检不应被伪装成一条用户创建的“分析任务”。具体复用和迁移范围需在第 2 轮实现时以当前实际表结构校验。
