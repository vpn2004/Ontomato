# ONN / PostgreSQL 多跳查询对照测试

测试日期：2026-11-06；108 隔离环境。使用 Ontomato v4.1.1、已提交的 T30 adapter，正式服务没有切换。

2026-11-07接续开发与同口径复验见[T32七跳执行链路优化](onn-core-t32-seven-hop-20261107.zh-CN.md)。下文保留本轮固定T30原始结果。

## 结论

跳数增加并不必然造成失控变慢，主要风险是每跳的关系展开量以及筛选所在位置。本轮已经复现：相同 7 跳问题，仅改变合法遍历起点就能明显减少 ONN 工作量；高扇出全量展开仍存在性能差距和硬限制。

以下耗时为完整应用请求的中位数，单位 ms；ONN/PG 大于 1 表示 ONN 更慢。

## 方法与数据

- 路径：同一个隔离 Workbench HTTP → 同一个 Java 21 Data Engine → 对应 adapter → 数据库 → 完整 JSON 响应；没有混入大模型生成时间。
- ONN 与 PG 各自独立容器，都限制为 2 CPU、3 GiB 内存，数据目录均为 tmpfs；没有清理宿主机缓存，主机仍运行其他服务。CPU 限额不等于独占 CPU，不能解释为纯引擎基准。
- ONN 使用固定 T30 Linux 包；adapter SHA256 为 `383c8ad1a4645c4bacdc288022bac9a752b86c71ea8360caf3d30f0391221de2`；PostgreSQL 18，使用属性 B-tree 索引并执行 ANALYZE。
- 真实质量夹具：29 类、1,979 对象、5,740 边。新构造控制图：8 类、128 对象、784 边，每层 16 个对象，分别构造每个对象连接下一层 1、2、4 个对象的关系。控制图很小，但候选路径数可快速增长，不能当作大数据容量验收。
- 控制图的分组等值连接在 PG 中产生的每一个对象对，与 ONN 中显式存储的边逐一相同；关系语义和路径重复次数一致。PG 全量对象回读与原始输入核对。
- 固定 1～7 跳、不同类型对象的内连接链路，不包含同类重复绑定、环和变长路径；7 跳是当前 adapter 支持的 8 对象边界。
- 六种查询：明细、完整路径计数、起点筛选计数、终点筛选计数、以筛选终点为起点的等价计数、终点对象去重计数。
- 预检 168 题 × 2 后端，共 336 次；ONN 164/168 通过、PG 168/168 通过。ONN 的 4 次失败均为明确预算拒绝，没有接受截断结果或错误答案。
- 163 个共同通过且适合完整比较的题目，每后端每题 3 块、每块 2 次预热后取 5 次，共 15 次正式样本；后端顺序交替、题目顺序固定随机化、单并发。
- 正式样本 4890 次，计时失败 0 次；所有成功样本均核对独立夹具期望值。
- 正式明细结果不声明排序，按完整多重集校验，保留重复路径。超过 5,000 路径的合成明细只作为窗口成员有效性/预算边界检查，不参与完整明细耗时比较；计数问题仍核对完整路径总数。

## 6. 已确认的失败边界

| ONN 用例 | 完整路径数 | 结果 |
|---|---:|---|
| synthetic_f4_h6_rows | 65,536 | `ONN POST /query/pipeline failed (HTTP 422, code=SNAPSHOT_TOO_LARGE)` |
| synthetic_f4_h7_rows | 262,144 | `ONN POST /query/pipeline failed (HTTP 422, code=BINDING_ROWS_EXCEEDED)` |
| synthetic_f4_h7_count | 262,144 | `ONN POST /query/pipeline failed (HTTP 422, code=BINDING_ROWS_EXCEEDED)` |
| synthetic_f4_h7_distinct_count | 262,144 | `ONN POST /query/pipeline failed (HTTP 422, code=BINDING_ROWS_EXCEEDED)` |

6 跳每跳 4 个关联的明细查询虽然用户只要求最多 5,000 行，当前 ONN 路径仍先物化完整 65,536 条 bindings，再分页和本地计算，因此可能在输出窗口前触发快照大小限制。对应 PG LIMIT 查询可以返回 5,000 条合法路径；这不表示 PG 在该请求中下载了全部 65,536 条明细。
这些是当前预算下的能力/性能限制，不是错误数据结果，也不意味着简单放宽内存或行数限制就能解决扩展性。

## 7. ONN 耗时在哪里

以下均为正式计数查询：COUNT 已下推且 bindingsRead=0。adapter 本地计算时间很小，主要时间花在远程 Core 的 evaluate；不应把这些计数耗时归咎于下载全部 bindings 后本地聚合。profile 阶段可嵌套，不能直接相加；read_keys/read_bytes 是逻辑读取计量，不是磁盘 I/O。

| 场景 | 应用总耗时 | adapter 远程读取 | adapter 本地计算 | Core evaluate | Core 逻辑 read_keys |

## 9. 测试期间发现的 Ontomato PG adapter 问题

初轮对多表同名字段排序时，PG adapter 生成不带表别名的 ORDER BY，例如 `ORDER BY "code"`，返回字段歧义；这属于 SQL 编译问题，不是 PostgreSQL 不支持关系查询。另有字符串排序与 Python 的码点顺序不同，正式测试不假设二者排序规则相同。
完整保存初轮排序诊断；随后双方统一使用不声明排序的明细 DSL，完整结果按多重集核对。没有为得到有利数字而修改任一 adapter 或数据库语义。

## 10. 后续优化顺序

1. Ontomato adapter / 规划：优先从明确 ID 或选择性较高的筛选对象开始遍历，保留关系方向和路径重复语义；本轮等价 DSL 已证明有收益，自动化仍需独立实现与回归。
2. ONN Core：优化大扇出的中间路径展开及原生 COUNT / DISTINCT 执行，减少对完整绑定结果的物化依赖；支持安全的过滤前移、执行顺序优化及可观察的阶段行数。
3. ONN Core 与 adapter：对语义允许的明细窗口支持安全提前裁剪，明确定义完整答案与完整源结果的证据区别；避免只取 5,000 行也必须物化全部路径。
4. Ontomato PG adapter：修复多表排序引用的别名/限定；后续另行评估多表 SQL 规划与计划复用，不能直接全局调小 join_collapse_limit。
5. 在完成上述优化后再扩大数据规模、关系密度和并发；本轮不能推出百万级对象、同类循环或变长路径的性能结论。
